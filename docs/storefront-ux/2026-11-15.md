## Research and references

- [Baymard — Form design](https://baymard.com/blog/form-design): prefer single-column checkout forms, persistent labels above fields, and minimize visible optional fields.
- [Baymard — Inline form validation](https://baymard.com/research-articles/inline-form-validation): validate at appropriate points and make corrections easy without premature error messages.
- [Baymard — Adaptive error messages](https://baymard.com/research-articles/adaptive-validation-error-messages): explain the specific input issue instead of generic invalid-field text.
- [Baymard — Checkout flow optimization](https://baymard.com/blog/checkout-flow-ux-optimization): linear steps, clear progress, preservation of entered data, and understandable recovery.
- [Christianbook — Bible filters](https://www.christianbook.com/apps/easyfind?N=1018567+4294862828+4294967135): translation, binding and format are real retailer facets; not evidence of this store's inventory. This is context from the catalog, not the checkout rationale.

## UX problem prioritized

Checkout address validation and network recovery are high-impact cases that deserve explicit visual treatment. The existing static filter annotations do not cover them. This run adds a **design specification**, not a functioning checkout.

## Actual editable Figma changes

Created `Checkout · Mobile · Address validation and recovery · 15 Nov 2026` (node `25:2`), a 1300 × 1180 comparison board with three mobile-style columns:
1. Address entry with persistent field labels, a linear progress indicator and optional apartment/unit disclosure.
2. Invalid email state with a specific correction message and preserved other entries.
3. Address-save network failure with retained fields and explicit retry action.

The board also annotates expected behavior: appropriate validation timing, focus/announcement of errors, preservation of nonsensitive form data and safe retries. Sample customer/address strings are explicitly illustrative. No product prices, shipping promises or payment integrations were fabricated.

## Decisions and assumptions

Keep existing Inter/blue/neutral tokens; do not adopt the unapproved green homepage concept. Preserve address data only according to application privacy requirements; do not persist raw payment-card data. The illustrated field labels and error messages require reconciliation with actual E07 and checkout schemas.

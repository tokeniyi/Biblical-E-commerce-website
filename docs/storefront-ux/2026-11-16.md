## Research reviewed

- [Baymard — Checkout flow optimization](https://baymard.com/blog/checkout-flow-ux-optimization) — clear inline errors, preserved entered values and reduced checkout effort.
- [Baymard — Adaptive validation errors](https://baymard.com/research-articles/adaptive-validation-error-messages) — targeted messages should identify the precise input issue and recovery action.
- [Baymard — Inline form validation](https://baymard.com/research-articles/inline-form-validation) — avoid premature error messaging and clear errors after correction.
- [Baymard — Current checkout UX](https://baymard.com/research-articles/current-state-of-checkout-ux) — explicitly identify required and optional fields, and avoid unnecessary form inputs.

These sources informed the checkout refinement. No claim is made that other named retailers were audited during this run.

## UX problem prioritized

The November 15 static address-validation board needed a more explicit comparison of recovery outcomes. Users should understand whether they need to correct a field, retry a failed save, or proceed after a confirmed successful save. This is a design-only specification, not implemented functionality.

## Actual editable Figma changes

Created **Checkout · Mobile · Error recovery refinement · 16 Nov 2026**, node `26:2`, 1250 × 1120 pixels with 82 editable children. Three 370px-wide illustrative mobile-state columns:

1. **Fix email:** specific error “Email address is missing the @ symbol” with correction path.
2. **Retry address save:** network failure message, retained nonsensitive form values, and explicit retry.
3. **Saved, continue:** successful-save confirmation and next-step action.

Each column includes a checkout step indicator, persistent field labels, a consistent primary action, and a recovery-oriented message. A behavior note specifies focus/error-summary behavior, appropriate validation timing, avoiding duplicate retries, and server-authoritative continuation. These are **design requirements**, not evidence of working behavior. Sample address/name data are placeholders.

## Decisions and assumptions

Maintain repository-approved Inter/blue/neutral design tokens. The progress indicator and checkout copy are illustrative and must be reconciled with the actual O03/E07 implementation. Do not store raw payment-card data in application state or claim a payment/order succeeded without authoritative server confirmation.
